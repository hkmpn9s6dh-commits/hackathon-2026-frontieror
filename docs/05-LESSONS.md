# 05-LESSONS — 這一輪學到什麼

寫給下一場用同一條生產線的人（也包括下一輪的我）。

## 1. 官方判分器在手上時，閘 B 可以做成「斷言即結論」——但要雙份

這場把 `feasibility_check.py` 原檔隨題發佈（「the code our evaluation runs on
every solution」）。好處是可行性不需要猜：跑它，就是評測的結果。壞處是**它會替
你把目標值也驗一遍**，於是很容易只信它、只信 solver 自報的 `objective_value`。

所以 `harness/objective.py` 另寫一份算式，從解的決定重算一遍，`AC-04` 要求兩邊
相等。這一條抓不到本輪的錯（六題都對得上），但它是**唯一能抓「解自洽但算錯」的
那道閘**，成本只有 60 行。

## 2. 成本與長度無關時，分支定界會朝錯的方向走

`hoffman1993` 的 15,000 個候選輪轉，成本 1–200、覆蓋 1–51 段，兩者**無關**。
於是最優解是「很多很短的輪轉」（成本低），而 CP-SAT 的第一個可行解是「很少很長的
輪轉」（33 根，成本 2,700+），之後每一步都要拆一根長的換幾根短的，60 秒內走不到
657 那種水準。

這不是調參能解決的：**要先知道最優解的形狀，再選搜索方向**。可複用的做法是
「先看成本/規模的散點，判斷最優解是長是短，再決定用構造還是用 B&B」。

## 3. 題目給的自由要用足，否則差距是兩位數百分比

`nagy2015` 明寫「送貨與取貨可以分兩趟、由不同車做」。第一版把同一顧客的送與取
綁在一條路線裡，結果 set-3（單一需求接近容量上限）每條路線只能裝一個顧客，
199 條路線、13,866；把送與取拆成**獨立任務**之後，同一批實例降到 13,711 並且
可以和其他顧客配對，平均分從 0.853 升到 0.942。

教訓：**先讀「題目允許什麼」，再讀「題目要求什麼」**。允許項往往是分數所在。

## 4. 沙箱限制要離線復刻，但復刻不了的部分要寫明

能復刻的：子進程、60 秒牆鐘、每題資料夾複製到暫存目錄、只寫 `/work/out`。
復刻不了的：真的 2 vCPU / 4 GB（本機沒有限制）、真的斷網（用 `AC-06` 掃
`import requests/urllib/socket/httpx` 代替）。

`docs/04-PROOF.md` 第 5 節把「這是模擬」寫在明面上。**不寫清楚，讀者會以為分數
是在真沙箱裡跑出來的。**

## 5. 早停比用滿時間更值

`barnhart2000` 原本跑滿 57 秒做 400 次重啟，改成「連續 300 次沒有更好的解就停」
之後，同樣的分數只要 2–10 秒（分數差 0.003）。把省下的時間留給真正需要預算的題
（`fischetti1998` 的 2-opt、`hoffman1993` 的 CP-SAT）比平均撒時間划算。

同時，**`--time-limit` 是硬牆**：留 5–7 秒餘量，別讓「寫檔」吃掉最後一秒。

## 6. 分數的方向搞反，會憑空造出一個好成績

本輪 `harness/verify.py` 只寫了「參考 ÷ 我們」這一支，於是**最大化**的定向越野
（`fischetti1998`）被算成 1.08–1.24，看起來「五個實例都比 Gurobi 好」。真相是
0.78–0.93：我們比參考差。整體平均也因此從 0.841 虛報成 0.891。

抓到它的是閘 D 的盲審（評委一句「OP 是最大化題，換算方向整頁沒交代」）。修法不是
改那幾個數字，而是把方向變成一个**單一來源**：`harness/directions.py`，驗證與合併
兩處都從它取，`scripts/merge_results.py` 一律用 `objective × reference` 重算，
不採信任何一輪寫進 JSON 的分數。

教訓：**只要有一個數字是「算出來的」，就只能有一個算式**。分數、百分比、差值都一樣。

參考值是估計這件事也照舊成立：基準的 Gurobi 目標 ≠ 比賽後台凍結的參考值，而且基準
沒附求解時間與 gap，所以我們連「參考離最優多遠」都不知道。報告裡不寫「贏」。

## 7. 一個實際的協作坑

這一輪開工時目錄裡已經有別條線在跑（賽道 AQ/AR），`MCB status` 的「當前單」被
後來的會話改寫成 AR。**同一個工作目錄只能有一個 `state.json` 指針**，所以：
自己的進度寫在 `STATE-<單號>.md`，不要覆寫共享的 `STATE.md`；收工也不要隨手
`MCB done`（會把別人的單標成 done）。
